# PostgreSQL Schema and Import Planning

This document covers KukGit PostgreSQL migration **Stage 2**. KukGit still runs on SQLite. These tools prepare table DDL, parameterized import operations and offline verification evidence; they do not connect to PostgreSQL or enable production cutover.

## Safety boundary

The SQLite export (`*.kgdb.json`) contains complete KukGit metadata, including password hashes, encrypted AuthKit and webhook material, session and token hashes, audit records, organization memberships and repository permissions. Protect it exactly like a production database backup.

The generated safe import-plan report does **not** contain row values. It contains table names, column names, row counts, batch offsets and SHA-256 SQL-template checksums. The PostgreSQL schema file contains DDL only.

A target snapshot is evidence supplied by a later PostgreSQL collector. Stage 2 can compare that evidence with the source manifest, but it does not independently query PostgreSQL. A verified Stage 2 receipt is therefore not sufficient to activate PostgreSQL runtime or cutover.

## Workflow

Create and verify a protected source export:

```bash
npm run database -- export \
  --output ./data/database-migration/kukgit-metadata.kgdb.json

npm run database -- verify-export \
  --input ./data/database-migration/kukgit-metadata.kgdb.json
```

Generate dependency-ordered PostgreSQL table DDL:

```bash
npm run database -- postgresql-schema \
  --input ./data/database-migration/kukgit-metadata.kgdb.json \
  --output ./data/database-migration/postgresql-schema.sql
```

Generate a secret-free import-plan summary:

```bash
npm run database -- postgresql-plan \
  --input ./data/database-migration/kukgit-metadata.kgdb.json \
  --batch-size 250 \
  --output ./data/database-migration/postgresql-import-plan.json
```

Verify a target snapshot generated by the later PostgreSQL adapter:

```bash
npm run database -- verify-postgresql-target \
  --input ./data/database-migration/kukgit-metadata.kgdb.json \
  --target-manifest ./data/database-migration/postgresql-target-manifest.json \
  --output ./data/database-migration/postgresql-target-verification.json
```

Create a checksummed receipt only after exact row-count and row-checksum verification:

```bash
npm run database -- postgresql-receipt \
  --input ./data/database-migration/kukgit-metadata.kgdb.json \
  --target-manifest ./data/database-migration/postgresql-target-manifest.json \
  --operator support@kuklabs.com \
  --output ./data/database-migration/postgresql-import-receipt.json
```

## DDL translation rules

Stage 2 currently translates:

- SQLite `INTEGER` to PostgreSQL `BIGINT`
- SQLite `REAL` to `DOUBLE PRECISION`
- SQLite `BLOB` to `BYTEA`
- declared `DATETIME` to `TIMESTAMPTZ`
- `TEXT DEFAULT CURRENT_TIMESTAMP` to an explicit PostgreSQL text cast
- `CREATE TABLE IF NOT EXISTS` to fail-fast `CREATE TABLE`
- SQLite `COLLATE NOCASE` and `AUTOINCREMENT` removal
- foreign-key dependency ordering before table creation

The planner fails closed when unsupported SQLite-only functions remain, a referenced table is missing, a cross-table dependency cycle exists, duplicate tables or columns are found, or an identifier would exceed PostgreSQL's 63-byte limit.

## Import operations

Import operations remain in process memory and use PostgreSQL positional parameters (`$1`, `$2`, ...). Row values are never serialized into the safe plan report. Binary wrappers from the SQLite export are restored to `Buffer` values and bigint wrappers are restored to `BigInt` values.

The later live executor must add a PostgreSQL parameter-count guard, transaction and lock policy, target-empty check, retry rules, cancellation, progress checkpoints and zero-secret logs before operations may run against a database.

## Target verification

A target snapshot must contain one record per table:

```json
{
  "engine": "postgresql",
  "tables": [
    {
      "name": "users",
      "rowCount": 10,
      "rowChecksum": "<64-character SHA-256>"
    }
  ]
}
```

Verification rejects missing tables, unexpected tables, duplicate names, row-count differences and row-checksum differences. A receipt binds the exact SQLite source fingerprint, schema-plan fingerprint, import-plan fingerprint and target fingerprint.

## Deliberately not included

Stage 2 does not provide:

- a PostgreSQL network client or connection pool
- schema creation on a live server
- row insertion on a live server
- secondary index or trigger migration
- PostgreSQL target-snapshot collection
- dual reads or dual writes
- runtime driver selection
- backup/restore for PostgreSQL
- cutover or rollback execution

Those remain under issue #43. Keep `KUKGIT_DATABASE_DRIVER=sqlite` until the live driver, import executor, target collector, dual-read validation and cutover gates are completed and reviewed.
